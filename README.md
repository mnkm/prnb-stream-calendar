# PROJECT NEBULA Stream Calendar

YouTube チャンネルの **動画・ショート・ライブ配信** と、Twitch の **配信・クリップ** をカレンダーで表示する Web アプリ。
Cloudflare Workers(静的アセット + Hono API)+ D1 + Cron Triggers で動作します。

> **ファンメイドの非公式ツールです。** PROJECT NEBULA および所属タレントの公式のものではなく、運営・タレントとは関係のない個人が作成・運用しています。

```
React SPA ──fetch──▶ Hono (/api/*) ──▶ D1
                                        ▲ upsert
        Cron (毎分) ───── sync ───────┘──▶ YouTube Data API v3 / RSS
                                          └▶ Twitch API (Helix)
```

画面を開くたびに YouTube や Twitch の API を呼ぶのではなく、Cron で定期的に取得して D1 に保存しておき、画面は D1 から読みます。表示が速く、API の 1 日の使用量(クォータ)も抑えられます。

## 主な機能

| 機能 | 内容 |
|---|---|
| 表示の切り替え | **月 / 週 / 日 / リスト** をヘッダーで切り替え。初期表示はパソコンなどでは週、スマホ(幅 768px 未満)ではリスト(URL の `view` で指定したときはその表示) |
| 月表示 | 種別ごとの色のチップで表示。1 日 4 件以上は「+N 件」から日別一覧を開く。スマホでは色の点のみ(日付を押すと日別一覧) |
| 週・日表示 | 0〜23 時を縦スクロールで表示し、予定を時刻の位置にブロックで置く。日付をまたぐ配信は始めた日の列に置き、24 時以降(25:00 など)まで表示を伸ばす。今日の列に現在時刻の線。日表示はサムネイル付き |
| リスト表示 | 月内の予定を日付ごとにサムネイル付きで表示。今月を開いたときは、予定が届いた時点で今日(今日に予定が無ければ次に予定がある日)の位置までスクロールする。ページを開いた直後はスクロールした状態から表示する |
| 詳細ダイアログ | 高画質サムネイル、日時・長さ、その場で再生(メンバー限定は YouTube へ誘導)。YouTube は「YouTube で開く」、Twitch は「Twitch で開く」のボタンで元のページへ移れる |
| セットリスト | 歌枠(タイトルに「歌枠」が無くても、歌った配信でセトリが見つかったもの)の詳細ダイアログに、番号・曲名・アーティスト・時刻(hh:mm:ss)の一覧を表示。時刻を押すとダイアログ内で、右のアイコンを押すと YouTube(スマホはアプリ)で、その位置から再生 |
| 期間の移動 | 前後ボタン、「今日」、カレンダーの左右スワイプ(タッチ操作のみ) |
| 種別フィルター | ライブ / 動画 / ショート / Twitch の表示切り替え(表示中の期間の件数付き)。件数は「ライブ」が YouTube のライブ、「Twitch」が Twitch の配信。Twitch の配信はライブに含まれるので、ライブを非表示にすると Twitch も表示されず、Twitch のボタンは押せなくなる |
| キーワード検索 | タイトルと、歌枠のセトリ(曲名・アーティスト)を全期間から検索。全角・半角、大文字・小文字を区別しない。セトリで当たった配信には、当たった曲をタイトルの下に表示する。結果はリストで全件たどれる |
| テーマ | 最初は OS の設定に合わせたライト / ダークで表示し、ヘッダーのボタンでライトとダークを切り替え |
| チャンネル情報 | ヘッダー右端の YouTube アイコンのボタンでチャンネル一覧を開き、チャンネルを選ぶと、バナー・@ハンドル・登録者数・動画数(Twitch があればフォロワー数も)を表示。名前の下に「YouTube で開く」「Twitch で開く」のボタンが同じ大きさで並び、その下に「楽曲リストを開く」ボタンがある。「チャンネル情報」(説明文、URL はリンク)・「再生リスト」・「クリップ」(Twitch にもチャンネルがある場合)のタブで切り替え、最初は「チャンネル情報」を開く |
| 楽曲リストへのリンク | 「楽曲リストを開く」は、各チャンネルで歌われた曲を探せる[タレント別楽曲リスト](https://mnkm.page/prnb-songlist/)を、そのチャンネルを選んだ状態(`?talent=`)で別のタブに開く。ボタンはチャンネルの色で表す(読みやすいよう、明るさをテーマに合わせて調整)。値を設定していないチャンネル(01 の公式)には出ない |
| 再生リスト | チャンネルの再生リストを全件カードで表示(おすすめ系を先頭、残りは最近動画が追加された順)。押すと中身の一覧を開き(「再生リスト順」「新しい順」「古い順」で並べ替えでき、スクロールで続きを自動で表示)、動画の詳細へ進める。動画の詳細には「この動画が入っている再生リスト」を表示し、そこから再生リストへ移れる |
| Twitch | Twitch にもチャンネルがあるメンバーは、Twitch の配信中のライブと過去の配信(アーカイブ)もカレンダーに表示する。Twitch の配信には「Twitch」の印が付き、詳細ダイアログでは Twitch のプレーヤーで再生する。チャンネル情報には Twitch へのリンクとフォロワー数を表示する |
| Twitch のクリップ | Twitch の配信の詳細ダイアログに「この配信のクリップ」を再生数の多い順に表示し、押すとダイアログ内で再生する。チャンネル情報の「クリップ」タブでは、カレンダーに無い配信のクリップも含めて、人気順・新しい順で見られる |
| 再生できなくなったもの | 取り込んだあとに非公開・削除された YouTube の動画や、公開が終わった Twitch のアーカイブは、記録を残したまま「再生不可」の印を付けて薄く表示し、詳細ダイアログには「この動画は再生できません」と確認した日付を表示する。YouTube で限定公開になったものには「限定公開」の印を付ける。削除された Twitch のクリップは一覧から外す |
| 複数チャンネル | 2 チャンネル目を登録すると、チャンネルフィルターと色分けが自動で表示される。ヘッダー左端にはサイトのアイコン(favicon と同じもの)を表示する(押しても動作しない) |
| 非公式の注記 | ページのいちばん下に、ファンメイドの非公式サイトであることと、情報の取得元(YouTube / Twitch)を表示する。同じ内容を `index.html` の `description` にも入れている |

表示の状態は URL に残るので、そのまま共有できます。

| パラメータ | 例 | 内容 |
|---|---|---|
| `view` | `month` / `week` / `day` / `list` | 表示モード |
| `date` | `2026-10-04` | 表示する日付(月・週表示ではその日を含む月・週) |
| `q` | `ASMR` | 検索語(指定すると検索結果を表示) |

以前の形式の `?month=2026-10` も開けます。

## API

| メソッド・パス | 内容 |
|---|---|
| `GET /api/channels` | 有効なチャンネルの一覧(名前・アイコン・色・説明・登録者数、Twitch のログイン名とフォロワー数、楽曲リストの talent の値など) |
| `GET /api/events?from=&to=&channels=&types=` | 期間内の予定(最大 100 日分)。カレンダー表示に使う。YouTube と Twitch の両方を返す |
| `GET /api/search?q=&types=&channels=&twitch=&cursor=` | キーワード検索(タイトルとセトリ)。50 件ずつ新しい順に返す(後述)。語は 5 個まで。`twitch=0` で Twitch の配信を除く。セトリで当たった予定には、当たった曲(`matchedSongs`)が付く |
| `GET /api/videos?channels=&types=&members=&before=&limit=&cursor=` | 動画の一覧(後述)。キーワードを使わずに、全期間を新しい順にたどる。ファンサイトのアーカイブなど、カレンダーの外から使うためのもの |
| `GET /api/setlist/:id` | 歌枠のセトリ(コメントの原文と書き手)。まだ見つかっていなければ 404 |
| `GET /api/morning-comments?channels=&limit=&cursor=` | 朝活の配信の、ボイスや今日の質問のタイムスタンプを含むコメント(後述)。ファンサイトの朝活のまとめページで使うためのもの |
| `GET /api/channels/:id/playlists` | チャンネルの再生リスト(おすすめ系が先頭、残りは最後に動画が追加された順) |
| `GET /api/playlists/:id` | 再生リストの中身(このカレンダーに登録済みの動画だけ、再生リストの並び順) |
| `GET /api/videos/:id/playlists` | 動画が入っている再生リスト |
| `GET /api/videos/:id/clips` | Twitch の配信に結び付いたクリップ(再生数の多い順、50 件まで) |
| `GET /api/channels/:id/clips?sort=&offset=` | チャンネルの Twitch のクリップ。`sort` は `popular`(再生数の多い順)か `new`(新しい順)。30 件ずつ返す。`offset` は 0〜3000 の整数(それ以外は 400)で、3000 件目より先は返さない |
| `POST /api/admin/sync` | 手動同期。`Authorization: Bearer <ADMIN_TOKEN>` が必要 |

`GET` の応答には、ブラウザ向けのキャッシュの指定を付けています(予定は 30 秒、それ以外は 1 分)。同期の結果が画面に出るまで、その分だけ遅れることがあります。検索と動画の一覧は、同じ期間 Cloudflare 側のキャッシュ(Cache API)にも置き、同じ問い合わせの繰り返しをデータベースを読まずに返します(検索はデータベースを全件読むため。動画の一覧は、終わった配信と公開済みの動画だけなので、少し古くても困らないため)。

### 動画の一覧(`/api/videos`)

YouTube の、配信が終わったものと公開済みのものを、新しい順に返します(`src/worker/db.ts` の `listVideos`)。

- **含めないもの**: 配信予定・配信中、公開前のプレミア公開(`live_status` が `upcoming` / `live`)、再生できなくなったもの(`unavailable_at` があるもの)、限定公開、Twitch の配信。YouTube で今見られるものだけにそろえるためです。
- **絞り込み**: `channels`・`types` は `/api/events` と同じです。`members` は `only`(メンバー限定だけ)/ `exclude`(メンバー限定を除く)/ 指定なし(すべて)。`before` を付けると、その日時より前のものから返します(年月を選んで読み始めるため。丸めません)。
- **ページ**: `limit`(1〜50、既定 50)件ずつ返し、続きは `cursor` に `nextCursor` を渡して取ります(形と並び順は `/api/search` と同じ)。
- **件数**: 最初のページ(`cursor` が無いとき)だけ、`counts` に種別ごとの件数(`live` / `video` / `short`)とメンバー限定の件数(`members`)が入ります。数えるのは、種別・メンバー限定・`before` の絞り込みの前です。
- 正しくない値(知らない種別、範囲外の `limit`、形の違う `cursor` や `before`)はエラーにせず、指定が無いものとして扱います。
- 1 つのチャンネルで絞り込むときは、`idx_videos_youtube_channel`(`channel_id, event_at`、YouTube の行だけ)を使います。

公開 API には、次の制限があります(`src/worker/index.ts`、回数は `wrangler.jsonc` の `ratelimits`)。

- **レート制限**: 1 つの IP(IPv6 は /64)から、API 全体で 1 分間に 200 回、キャッシュに無い検索は 1 分間に 30 回まで。超えると `429`(`Retry-After: 60`)を返します。数えるのは Cloudflare の拠点ごとなので、厳密な上限ではありません。
- **入力の上限**: `/api/events` の期間は 15 分単位に広げて扱います。パスの ID は英数字と `_` `-` `:` の 64 文字までで、それ以外は `404` です。`cursor` は `nextCursor` の形のものだけを受け付けます。

画面(静的ファイル)の応答には、`public/_headers` で CSP などのヘッダーを付けています。開発サーバー(`npm run dev`)では付かないので、読み込み先(外部の画像・フォント・埋め込み)を足したときは、`npm run preview` で確かめてください。

### 朝活のコメント(`/api/morning-comments`)

タイトルに「朝活」を含む配信(`【朝活】` のほか `【Minecraft/朝活】` なども)の、ボイス(ボイスマロ)や今日の質問のタイムスタンプを含むコメントを返します(`src/worker/db.ts` の `listMorningComments`)。そういうコメントがある配信(と、下の目で確かめて足したボイスがある配信)だけを、配信の新しい順に返します。

```json
{
  "videos": [
    {
      "videoId": "9aWJhQ2IEek",
      "channelId": "UC4g6i7aL2fn2EME3r9fEHxA",
      "title": "【朝活】…",
      "eventAt": "2026-10-20T22:00:00Z",
      "endedAt": "2026-10-21T00:30:00Z",
      "comments": [
        { "id": "Ugx…", "author": "@…", "authorChannelId": "UC…", "text": "…\n   01:49:23 ゆられんデートボイス🎤\n…", "likeCount": 3 }
      ],
      "manualVoices": []
    }
  ],
  "nextCursor": "2026-10-20T22:00:00Z~9aWJhQ2IEek"
}
```

- **選ぶコメント**: 同じ書き手の返信をつなげたもの(下の「6-2」)で、時刻(`1:23`・`01:23:45`)の行が 2 行以上あり、そのどれかに「ボイス」「マロ」「🎤」「今日の質問」のどれかがあるコメント(`src/shared/morning.ts` の `hasMorningStamp`)。1 本の配信で 10 件まで保存します。本文はコメントの原文のままで、行の読み取りは使う側で行います。`comments` は関連性順(YouTube の並び)です。
- **目で確かめて足したボイス(`manualVoices`)**: コメントからは「ボイス🎤」の形で読み取れない回のボイスを、`{ "time": "02:21:24", "name": "1回目🎤（エコーなし）", "commentId": "Ugx…" }` の形で、時刻の順に返します(無い回は空の配列)。中身は `src/worker/morning-manual.ts` に手で書いたもので、公開の朝活 501 本のうち「ボイス🎤」の行が無かった 212 本を、ユーザーが目で確かめた結果です(2026-10)。`commentId` はその行があるコメントの id(返信なら返信の id。`https://www.youtube.com/watch?v=<videoId>&lc=<commentId>` で開けます)で、分からなければ `null` です。ここにある配信は、保存したコメントが無くても返します。使う側では、コメントから読み取ったボイスに、これを足して使ってください。
- **本文は誰でも書いたもの**: ファンのコメントの原文なので、使う側では HTML として埋め込まず、文字として扱ってください(エスケープする)。
- **`&gt;` などが残る**: YouTube は `textFormat=plainText` でも、`>` などを `&gt;` の形で返すことがあります(実際の朝活のコメントに「#&gt;  ボイス🎤」がありました)。表示する前に、`&amp;` `&lt;` `&gt;` `&quot;` `&#39;` を元の文字に戻してから、エスケープしてください。
- **含めないもの**: メンバー限定・限定公開・再生できなくなった配信、Twitch の配信。
- **絞り込みとページ**: `channels` は `/api/events` と同じです。`limit`(1〜50、既定 50)本ずつ返し、続きは `cursor` に `nextCursor` を渡して取ります(形と並び順は `/api/videos` と同じ)。正しくない値は指定が無いものとして扱います。
- 応答は Cloudflare 側のキャッシュにも 5 分置きます(コメントは配信終了から 30 日後まで取り直すので、少し古くても困らないため)。

### 配信の場所(サブパス)

このサイトは、別の Worker(プロキシ)からサービスバインディングで呼ばれ、`https://mnkm.page/prnb-stream-calendar/` というサブパスで配信される想定です。プロキシは、先頭の `/prnb-stream-calendar` を外してからこの Worker に渡すので、この Worker から見たパスは、これまでどおり `/`、`/api/…`、`/assets/…` です(上の表のパスも、この Worker から見たものです。ブラウザからは、先頭に `/prnb-stream-calendar` が付きます)。

- 画面が読み込むファイル(スクリプト・CSS・`theme.js`・favicon)と、画面からの API の呼び出しは、**ページからの相対指定** にしています(`vite.config.ts` の `base: './'` と、`src/client/lib/api.ts` の `api/…`)。同じビルドが、サブパスでも、ルート(ローカルの開発サーバー、プレビュー)でも動きます。
- 画面の URL はパスを持たず、状態はクエリ(`?q=` など)だけです。存在しないパスには 404(`public/404.html`)を返します(`wrangler.jsonc` の `not_found_handling`)。どのパスにも画面を返す設定にすると、深いパスで開いたときに相対指定の基準がずれて、画面が真っ白になります。**画面にパスを持つページを足すとき、または API を `/api/…` のようにルートから指定するときは、サブパスで動かなくなる** ので注意してください。
- プロキシは、元のリクエストのヘッダーを引き継いで渡す必要があります(公開 API のレート制限が、`CF-Connecting-IP` でアクセス元を見分けるため)。また、この Worker が返すリダイレクト(`/index.html` → `/` など)の `Location` は、この Worker から見たパスなので、プロキシで先頭に `/prnb-stream-calendar` を足します。
- workers.dev の URL(`https://prnb-youtube-calendar.<アカウント>.workers.dev`)は閉じています(`wrangler.jsonc` の `workers_dev: false`)。本番の入口は `https://mnkm.page/prnb-stream-calendar/` だけです。

## データモデル(D1)

### `videos`

| 列 | 内容 |
|---|---|
| `id` | 動画 ID |
| `type` | `live` / `video` / `short` |
| `live_status` | `upcoming`(予定)/ `live`(配信中)/ `ended`(終了)。ライブとプレミア公開のみ |
| `event_at` | カレンダーに置く日時(UTC)。ライブ・プレミアは開始(予定)時刻、それ以外は公開日時 |
| `ended_at` | 配信の終了日時 |
| `duration_sec` | 動画の長さ |
| `members_only` | メンバー限定なら 1 |
| `search_title` | 検索用に正規化したタイトル(後述) |
| `platform` | `youtube` / `twitch` |
| `twitch_video_id` | Twitch のアーカイブの動画 ID。配信中でまだ無い・保存されていない・公開が終わった場合は NULL |
| `unavailable_at` | 取り込んだあとに再生できなくなった(非公開・削除・公開終了)と確認した日時。再生できるあいだは NULL |
| `unlisted` | YouTube で限定公開なら 1 |
| `missing_count` / `availability_checked_at` | 再生できるかの確認で、続けて返ってこなかった回数と、最後に確認した日時 |

ほかに `title`、`thumbnail_url`、`published_at`、`updated_at` など。Twitch の行の `id` は `twitch:` + 配信の ID で、`type` は `live` です。

### `setlists`

歌枠のセトリ。コメントの原文(`text`)と書き手(`author`)、確認した日時(`checked_at`)、次に確認する日時(`next_check_at`)を持ちます。曲名・アーティスト・時刻への読み取りは表示のときに行うので、原文のまま保存しています。最後に点検した日時(`audited_at`)も持ちます。

キーワード検索のために、読み取った曲も保存しています。`songs` は曲名とアーティストの JSON、`search_songs` は検索用にそろえた文字列(1 曲 1 行)、`songs_version` は読み取りに使った規則の版です。

### `morning_comments` / `morning_checks`

朝活の配信の、ボイスや今日の質問のタイムスタンプを含むコメント(`morning_comments`)と、コメントを確認した記録(`morning_checks`)。`morning_comments` はコメントの原文(`text`)、書き手(`author`・`author_channel_id`)、高評価の数(`like_count`)、関連性順の位置(`position`)を持ちます。コメントを全部見られた確認では、その配信の分を入れ替えます(下の「6-2」)。`morning_checks` に行が無い配信は、まだ一度も確認していないものです。

### `setlist_audits`

セトリの点検で問題が見つかった歌枠。問題の内容(`problems`、JSON)、同じ問題を何度も知らせないための目印(`signature`)、見つかった日時(`found_at`)、Issue で知らせた日時(`notified_at`)を持ちます。問題が無くなれば行を消します。

### `playlists` / `playlist_items`

チャンネルが作った公開の再生リストと、その中身(どの動画が何番目に入っているか)。`items_synced_at` が NULL の再生リストは、中身の読み直しが必要なことを表します。

### `channels`

同期対象のチャンネル。`color`(複数チャンネル時の識別色)、`label`(表示・非表示ボタンに出す短いラベル)、`enabled`、プロフィール(`description` / `custom_url` / `banner_url` / `subscriber_count` / `video_count`、1 日 1 回更新)、過去分の取得の進み具合(`backfill_stage` / `backfill_page_token`)、一度だけ行う補正の進み具合(`premieres_*` / `members_*`)、Twitch のログイン名と同期の状態(`twitch_*`)、楽曲リストのサイトで使う talent パラメータの値(`songlist_talent`)を持ちます。

### `twitch_clips`

Twitch のクリップ。タイトル、作った人(`creator_name`)、再生数(`view_count`)、長さ、サムネイル、作成日時と、元の配信(`event_id`。`videos.id`)を持ちます。カレンダーに無い配信のクリップは `event_id` が NULL です。今もあるかの確認のために、続けて返ってこなかった回数(`missing_count`)と最後に確認した日時(`checked_at`)も持ちます。

### `twitch_auth`

Twitch API のアクセストークン(1 行だけ)。約 60 日有効で、期限が近づくと同期のときに取り直します。

## 同期の仕組み

Cron は毎分動きます(Workers Paid プランが前提)。5 分に 1 回は **全体の同期**、それ以外の回は、配信の開始・終了だけを見る **軽い確認** です(`src/worker/index.ts` の `scheduled`)。

全体の同期は、次の順に処理します。新着と配信の状況を先に確認し、残りで時間のかかる処理を進めます。

| 順 | 処理 | 進め方 |
|---|---|---|
| 1 | YouTube の差分同期(新着・配信の状況) | 毎回、全チャンネル(5 分ごと) |
| 2 | Twitch の同期 | 配信中のライブは毎回、全チャンネル分。アーカイブは 1 回に 1 チャンネル、クリップは 1 回に 100 件 |
| 3 | 過去分の取得 | チャンネルを登録した直後だけ |
| 4 | 一度だけの補正 | 過去分の取得のあと、終わるまで |
| 5 | セットリストの確認と、曲の読み取り | 確認は 1 回に 10 本、読み取りは 1 回に 50 本 |
| 6 | セットリストの点検と通知 | 点検は 1 回に 50 本、通知は 1 日 1 回 |
| 6-2 | 朝活のコメントの確認 | 1 回に 5 本(過去の配信も、これで少しずつ取り込む) |
| 7 | 再生リストの同期 | 一覧は 1 日 1 回、中身は本数が変わったものだけ |
| 8 | 再生できるかの確認 | 1 回に 50 本、各動画 1 日 1 回 |

あわせて、チャンネルのプロフィール(`channels.list` の snippet / statistics / brandingSettings)を 1 日 1 回取り直します(1 ユニット)。同期の最後には、検索用の列(`search_title`)が空の行を 1 回あたり 1,000 件ずつ埋めます(列を追加する前に登録した行のための処理で、全部埋まっていれば読み取り 1 回だけです)。

### 軽い確認(毎分。配信の開始・終了)

全体の同期の合間(5 分のうち 4 回)に、`syncLiveStatus` が次のことだけを行います。

- **配信中のもの** と、**開始の予定が 6 時間前〜10 分先にある配信予定**(全チャンネル)を、まとめて `videos.list` で取り直します(50 本まで 1 ユニット)。この範囲に入っている配信は、開始・終了、予定時刻の変更が、最大 1 分ほどでデータベースに反映されます(画面に出るまでには、ブラウザのキャッシュ 30 秒と、開いたままの画面の取り直し 1 分が加わります)。予定より 10 分以上早く始めた配信や、待機所を作らずに始めた配信は、全体の同期(5 分ごと)で反映されます。
- 見る配信が無いときは、YouTube には問い合わせません(クォータを使いません)。何か月も先の予定で置かれている待機所は、始まる時刻が近づくまで対象になりません。
- 新しい配信予定の検知と、消えた配信(削除・非公開)の扱いは、全体の同期(5 分ごと)に任せます。
- Twitch の配信中の確認は、全体の同期のとき(5 分ごと)だけです。

### 実行の上限(Workers Paid プラン)

Workers Paid プランでは、1 回の実行の CPU 時間が 30 秒まで(Cron の間隔が 1 時間未満の場合)、サブリクエスト(外部への fetch と D1 の呼び出し)が 10,000 回まで、D1 の問い合わせが 1,000 回までです。同期処理は、暴走の歯止めとして、1 回の実行で使うサブリクエストを 300 回の予算(`src/worker/budget.ts` の `RequestBudget`)で数えています(D1 の `batch()` は 1 回として数える)。

- 差分同期は 1 チャンネルあたり、ふつう最大 11 回(YouTube 5 回 + D1 4 回 + プロフィールを取り直す日は 2 回)、Twitch の同期は最大 9 回です。RSS が取れなかった回は 1 回、ショートの一覧が無いチャンネルは、新しい動画を URL で確かめる分だけ増えます。
- 予算が足りなくなったとき(チャンネルを登録した直後の過去分の取得が重なったときなど)は、後ろの処理(セトリ → 朝活のコメント → 再生リスト → 再生できるかの確認)から、次の実行に回ります。
- 無料プランでは動きません(CPU 時間 10ms、サブリクエスト 50 回の上限に収まりません)。

### YouTube のクォータを使い切ったとき

YouTube Data API のクォータ(1 日 10,000 ユニット)を使い切ると、その日は YouTube への問い合わせがすべて 403 になり、太平洋時間の 0 時(日本時間の 16 時または 17 時)に戻るまで、YouTube の同期が止まります(Twitch の同期と、画面の表示は続きます)。下の「クォータの目安」を超えそうな変更(チャンネルの追加、同期の間隔を縮める)をするときは、先に見積もってください。


### 1. YouTube の差分同期(過去分の取得が終わったチャンネル)

- RSS(クォータを消費しない)で新着を検知します。YouTube の RSS に出るまでの遅れは、こちらでは縮められません。
- メンバー限定は RSS にも `UU…` にも含まれないため、メンバー限定のプレイリスト(`UUMO…`)の先頭も確認します。
- 新着と「予定・配信中」のライブだけを `videos.list` で取得し直します。予定時刻の変更や配信の開始・終了が反映されます。
- 種別の一覧(ショートの `UUSH…`、動画タブの `UULF…`)の先頭は、**新しい動画があった回**、**公開から 1 時間以内のライブ以外の動画がある回**、**1 時間に 1 回の確かめ直しの回** にだけ確認します(毎回確認すると、1 チャンネルにつき 2 ユニットずつ使うため)。公開されたばかりのショートは、一覧に載るのが遅れていったん「動画」として登録されることがありますが、公開から 1 時間は毎回確かめ直すので、5 分ほどで直ります。1 時間に 1 回の確かめ直しは、時刻とチャンネルの並び順から回を決めています(状態は持ちません。実行が 1 回抜けると、そのチャンネルの確かめ直しは次の 1 時間後になります)。
- 始まらないまま待機所が削除・非公開になった配信予定は、`videos.list` に返ってこないので、カレンダーからも消します。配信中に返ってこなくなった配信(配信のあとすぐ非公開にされたもの)は、記録を残して「再生不可」にします。

### 2. Twitch の同期(毎回)

`channels.twitch_login` が入っているチャンネルが対象です。YouTube のクォータは使わず、サブリクエストは 1 回の実行で 4〜6 回(最大 9 回)です。`TWITCH_CLIENT_ID` / `TWITCH_CLIENT_SECRET` が無ければ何もしません。

- **アクセストークン**: アプリ用のトークン(約 60 日有効)を D1 に保存して使い回し、期限の 1 日前になると取り直します。無効になっていたら(401)消して、次の実行で取り直します。
- **配信中のライブ**: 全チャンネル分を 1 回のリクエストで確認します(5 分ごと)。配信中の一覧から消えた配信は「配信済み」にします。Twitch には待機所が無いので、配信予定は取り込みません。
- **アーカイブ**: 1 回の実行で 1 チャンネルずつ、新しい 20 件を確認します。配信が終わったばかりのチャンネルを先に確認し、長さとアーカイブの動画を反映します。配信中の行とアーカイブは配信の ID で同じ行にまとめます(行の ID は `twitch:` + 配信の ID)。
- **1 日 1 回**: チャンネルごとにユーザー ID とフォロワー数を取り直し、アーカイブを 100 件まで確認します。
- **公開が終わったアーカイブ**: 1 日 1 回の確認で一覧から消えていたアーカイブ(保存期間を過ぎたもの)は、カレンダーの記録を残したまま、`unavailable_at` を入れて「再生不可」にします。最初から保存されていない配信(配信中に取り込んだ記録だけがあるもの)は「再生不可」にはせず、「この配信のアーカイブはありません」と表示します。
- **クリップ**: 1 回の実行で 1 チャンネル・100 件ずつ確認します。最近 1 週間に作られたクリップは 1 時間ごとに確認し(再生数も新しくなります)、その合間に全期間のクリップを再生数の多い順に 1 ページずつ読み進めます。全期間は 1 週間ごとに読み直します。
- **クリップと配信の結び付け**: クリップに元のアーカイブの動画 ID があれば、そのアーカイブの配信に結び付けます。無ければ(アーカイブが無い配信)、クリップを作った時刻が開始〜終了に入っている配信に結び付けます。どちらにも当てはまらないクリップは、チャンネル情報の「クリップ」タブにだけ出ます。
- **クリップの削除の確認**: 取り込み済みのクリップが今もあるかを、1 回の実行で 50 本ずつ、各クリップ 1 日 1 回確認します。2 回続けて返ってこなければ、削除されたものとして行を消します。
- ハイライトとアップロード動画は取り込みません。

### 3. 過去分の取得(チャンネル登録直後)

1. 全アップロードのプレイリスト(`UU…`)を、予算の残りの範囲で 1 回あたり最大 8 ページ(400 件)ずつ取得し、数回の Cron に分けて進めます。
2. 最後まで取得したら、ショートのプレイリスト(`UUSH…`)でショートを判定します。

### 4. 一度だけの補正(過去分の取得のあと、終わるまで続ける)

- **プレミア公開**: 「動画」タブのプレイリスト(`UULF…`)を最後まで見て、ライブとして登録されたプレミア公開を動画に分類し直します。
- **メンバー限定**: `UUMO…` を最後まで取り込み、`UUMF…` でメンバー限定のプレミア公開を判定します。

どちらも、過去分の取得と同じく、残りの予算の範囲でページ単位に進め、続きは次の実行に持ち越します。

### 5. セットリストの確認と、曲の読み取り

タイトルに「歌枠」を含む、配信が終わった歌枠(メンバー限定を除く)のコメントを確認し、セトリを保存します。

タイトルに「歌枠」が無い配信(お知らせや雑談のあとに歌った配信など)も、**終了から 7 日以内のものだけ** を確認します(過去の配信はさかのぼりません。約 1,800 本あり、確認するとクォータが一度に増えるため)。歌っていない配信の方が多いので、選び方を厳しくします。

- **セトリらしい書き方のコメント** だけを候補にします。「セトリ」の見出しがあるか、曲番号(`【01】`・`01.`・`M01`・`No.01`)のある時刻の行と歌の印(🎵・♪ など、「(歌)」)のある行が合わせて 3 行以上あるもの(`hasSetlistMarks`)。曲として読めるかだけでは、ゲームの章立て(「Chapter1 - 森の村」)や雑談の目次(「近況 / 引っ越しの話」)もセトリとして読めてしまうためです。番号も印も無い「時刻 曲名 / アーティスト」だけのセトリは、雑談の目次と見分けられないので取りません(保存済みの歌枠のセトリで試すと、約 95% はこの条件を満たします)。
- その中で、曲として 3 曲以上読めたものだけを保存します(確かめられなかった候補は使いません)。
- 確認は配信終了の **1・6・24 時間後、3・7 日後** の 5 回です。同じ回に確認する配信が多いときは、歌枠を先に確認します。
- 7 日たっても見つからなかったものは、点検で「見つからない」として知らせません。
- 7 日を過ぎた配信を確認し直させたいときは、`setlists` に `next_check_at` を過去にした行を入れます(`migrations/0017_recheck_split_setlists.sql` と同じやり方)。

- コメントを関連性順で 20 件取得し(1 ユニット)、**タイムスタンプを 3 個以上含むコメント** をセトリの候補とします。候補を **配信者本人のコメント → 高評価の多いコメント → 関連性順で上のコメント** の順に並べ、上から順に実際に読み取ってみて、**曲として 3 曲以上読めた最初のコメント** を選びます(時刻つきの感想のように、時刻はあってもセトリではないコメントを選ばないため。感想が何件も上に並んでいても、その下にあるセトリを選べるよう、読めるものが見つかるまで候補を全部確かめます)。どれも読めないときは、並べた先頭の候補を選びます(読み取りの規則に合わない新しい書き方のセトリを捨てずに保存し、下の点検で気づけるようにするため)。公式 API には「固定コメント」の印が無いので、固定されているかどうかは選び方に使えません。
- 曲の多い歌枠では、セトリが 1 つのコメントに収まらず、同じ書き手が返信に続き(「セトリ②」など)を書くことがあります。選んだコメントに返信があれば、100 件までを取り(もう 1 ユニット。実際の応答は古い順に返ってきますが、API の仕様として決まっているわけではありません)、**同じ書き手の、セトリの続きに見える返信** を、書かれた順につなげて保存します。続きとみなすのは、時刻が 3 個以上ある返信と、最初の行が「セトリ」の見出しか時刻で始まる返信です(ほかの人の返信や、お礼・雑談の返信は入れません)。
- コメントは誰でも書けて 1 件 10,000 文字まであるので、応答は最大で数 MB になりえます。暴走の歯止めとして、応答が 5MB を超えた歌枠は、その回は解析せずに次の確認まで後回しにします(ふつうの歌枠の応答は 10〜16KB ほど)。
- 返信を読めなかったとき(応答が大きすぎる、そのコメントの返信だけが取れない)は、最初のコメントだけで考えます。まだ何も保存されていなければ、最初のコメントだけを保存します。保存済みと同じコメントなら、**保存済みを残します**(保存済みは返信をつなげたものかもしれず、誰でも書ける長い返信だけで短くされないようにするため)。保存済みと違うコメントなら、保存済みより長いときだけ置き換えます。
- 曲として読めると確かめられなかった候補は、まだセトリが保存されていない歌枠にだけ使い、**すでに保存してあるセトリは置き換えません**(時刻つきの感想が上位に並んだだけで、前に取れた正しいセトリが消えないようにするため)。
- 配信終了の **15 分後・30 分後、1・6・24 時間後、3・7 日後** に確認します。セトリが見つかったあとも 7 日後までは確認を続け、より良い候補(配信者本人のコメント、高評価の多い読めるコメント)があれば差し替えます(その回に候補が無ければ、前に見つけたものを残します)。7 日を過ぎたら確認をやめます。コメントが無効な配信は 1 回でやめます。早い時刻の確認では、書きかけのセトリや時刻つきの感想が先に保存されることがあります(あとの確認で置き換わります)。
- 1 回の実行で確認するのは 10 本まで。過去の歌枠は新しいものから順に 1 回ずつ確認します。
- 見つかったセトリは、同じ実行の中で、表示と同じ読み取り(`parseSetlist`)で曲名・アーティストを取り出し、検索用に保存します(1 回の実行で 50 本まで)。読み取るのは、コメントの先頭 **250 行・6,000 文字まで** です(実際のセトリは、1 つのコメントに収まるもので 60 行・1,500 文字ほど、返信をつなげた 100 曲のもので 140 行・4,000 文字ほど。読み取りは閲覧者のブラウザでも動くので、細工された長いコメントで時間がかからないように切っています。上限は `src/shared/setlist.ts` の `SETLIST_MAX_LINES` / `SETLIST_MAX_CHARS`)。上限を超えたコメントは途中までしか読まれないので、下の点検で知らせます。読み取りの規則の版(`SETLIST_PARSER_VERSION`)が変わると、全部を読み取り直します。

- **1 件あたりの大きさの上限**: セトリのもとになるコメントは誰でも書けるので、1 件あたりの大きさには上限を設けています(読み取りは 6,000 文字・250 行まで、YouTube の応答は 5MB まで)。上限いっぱいに細工されたコメントが本数の上限まで並んでも、1 回の実行は 1〜2 秒ほど(開発機での見積もり)で、CPU 時間の上限(30 秒)に収まります。


### 6. セットリストの点検と通知

書き手が変わるなどして、読み取りの規則に合わない書き方のセトリが出てきたことに気づくための仕組みです。YouTube のクォータは使いません。

- **点検**: 取得したセトリ(と、7 日たっても見つからずにあきらめた歌枠)を、サイトの表示と同じ読み取り(`parseSetlist`)にかけて点検します(`src/shared/setlist-audit.ts`)。1 回の実行で 50 本まで。見るのは次のとおりです。
  - セトリが見つからない(タイトルに「歌枠」がある配信だけ) / 時刻があるのに曲が 1 曲も読み取れない / 曲が 2 曲以下
  - コメントが読み取りの上限(250 行・6,000 文字)を超えていて、途中までしか読んでいない(実際のセトリで出たら、上限を上げる)
  - 曲以外(開始・挨拶・告知など)が曲として出ている / 曲名・アーティストに時刻・区切り記号・「※」が残っている
  - 時刻が前の曲より前・配信の長さを超えている / アーティストが空 / 曲名・アーティストが長すぎる
- **通知**: まだ知らせていない問題があれば、毎日 **9 時(JST)** を過ぎた最初の実行で、GitHub に Issue を 1 つ作ります(ラベル `setlist-check`、1 日 1 回、20 本まで)。Issue には動画のリンク、理由、該当する曲、元のコメントを載せます。
- Issue は持ち主のトークンで作るため、GitHub は持ち主に通知しません。そこで GitHub Actions(`.github/workflows/setlist-check-notify.yml`)が、作られた Issue に持ち主へのメンション付きのコメントを付け、メールなどで通知が届くようにしています。
- **同じ内容は二度と知らせません**。コメントと問題の内容(種類と該当する曲)が同じなら、取り直しても通知しません。読み取りの規則を直して結果が変わったときや、別のコメントに変わったときだけ、もう一度知らせます。問題がなければ Issue を閉じるだけで構いません。
- 読み取りの規則を直しても、点検済みのセトリは点検し直しません(取り直したときに点検します)。
- `GITHUB_TOKEN` が無ければ、点検だけ行い通知しません。

### 6-2. 朝活のコメントの確認(残りの予算で)

タイトルに「朝活」を含む、配信が終わった配信(メンバー限定・限定公開を除く)のコメントを確認し、ボイスや今日の質問のタイムスタンプを含むものを保存します(`src/worker/sync.ts` の `checkMorningComments`。選び方は上の「朝活のコメント」)。

- コメントを関連性順で 100 件、それぞれの返信の一部(多くて 5 件ほど)と一緒に取得します(`commentThreads` の `part=snippet,replies`、1 ユニット)。長いタイムスタンプは、書き手が自分のコメントへの返信に続きを書く(「◇ 最後まで ◇」など)ので、**同じ書き手の返信を、書いた順に空行をはさんでつなげてから** 選び、つなげたものを保存します(`mergeMorningReplies`、20,000 文字まで)。2024 年の配信では、ボイスの行は返信の中にしかありません。付いてきた返信が全部でなく、本体か付いてきた自分の返信に時刻の行があるときだけ、残りの返信を取り足します(`comments.list`、1 件 1 ユニット、1 本の配信で 3 回まで。過去の朝活 501 本を調べた時点では、返信はどれも 5 件以下で、取り足しは要りませんでした)。返信込みの応答が 5MB を超えたときは、返信なしで取り直します。
- 朝活のコメントは多くても数十件なので、ふつうは全部を見られます。タイムスタンプのコメントが関連性順の最後に来ることもあるため、セトリの確認(20 件)より多く取ります。100 件を超える配信では、101 件目より後のコメントは見落とします。
- 確認は配信終了の **3・24 時間後、3・7・30 日後** の 5 回です。タイムスタンプのコメントは、配信の翌日以降に書かれたり書き足されたりすることもあるためです。
- コメントを全部見られたとき(100 件未満で、取り足さなかった・取れなかった返信が無く、選んだものが 10 件以下)は、その配信の分を今回選んだものに入れ替えます(消された・書き直されたコメントを反映するため)。全部見られなかったときは、今回選んだものを書き足すだけで、保存済みは消しません(見られなかった分に、前に選んだコメントがあるかもしれないため。ただし 10 件を超えた分は、関連性順で下のものから消します)。
- コメントが無効・動画が見つからない(一時的に非公開になったなど)ときは、保存済みを残し、確認は予定どおり続けます。
- **過去の配信**: まだ一度も確認していない配信は、新しいものから順に 1 回ずつ確認します(最後の確認の時刻を過ぎているので、1 回で終わります)。1 回の実行で 5 本まで(1 時間に約 60 本)。約 510 本なら、合わせて約 510 ユニット、9 時間ほどで終わります。そのあいだは、後ろの処理(再生リスト・再生できるかの確認)に回る予算が、1 回あたりふつう 7 回分ほど減ります(返信の取り足しが要る配信があると、1 本あたり最大 3 回増えます)。
- その動画だけの失敗(非公開になったなど)は、保存済みのものを残して次の確認まで後回しにします。クォータ超過など、ほかの動画でも同じように失敗するときは、そこで止めて次の実行に回します。

### 7. 再生リストの同期(残りの予算で)

- 各チャンネルの再生リストの一覧を **1 日 1 回** 取り直します(`playlists.list`、1 ユニット)。消えた再生リストは中身ごと削除します。
- **本数が変わった再生リスト(と新しい再生リスト)だけ**、中身を最初から読み直します(`playlistItems.list`、1 ページ 50 件で 1 ユニット)。1 回の実行で読むのは 8 ページまでで、続きは次回に持ち越します。
- おすすめ系(タイトルに「初見」「はじめて」「初めて」「まずはこれ」を含むもの)は、一覧の先頭に固定します(`src/shared/playlist.ts`)。メン限の再生リストも同じように表示します。
- 再生リストの中に、このカレンダーに無い動画(非公開・削除済みなど)があれば、本数には数えますが一覧には表示しません。

### 8. 再生できるかの確認(残りの予算で)

取り込み済みの YouTube の動画・ショート・終わった配信が、今も再生できるかを確認します。

- 1 回の実行で 50 本を `videos.list` で問い合わせます(1 ユニット)。まだ確認していないもの、最後の確認から 1 日たったものを、古い順に確認します。約 4,200 本なら 84 回の実行(約 7 時間)で一巡し、1 日 84 ユニットほどです。
- 非公開・削除された動画は返ってこないので、**2 回続けて返ってこなければ**「再生不可」にします(1 回目は次の実行でもう一度確認します)。取得に失敗したとき(クォータ超過など)は、何も変えません。
- 再び返ってくるようになれば「再生不可」を外し、配信の状態や長さも取り直します。
- 同じ問い合わせで公開状態も分かるので、限定公開になったもの・公開に戻ったものも反映します。

### 種別の判定

| 種別 | 判定方法 |
|---|---|
| ライブ | `liveStreamingDetails` があるもの |
| プレミア公開 | API ではライブと同じ形で返る。`UULF` / `UUMF` に含まれる、または公開前・公開中で動画の長さがある(ライブ配信は長さ 0)ものを **動画** として扱う。ライブ配信も終わった直後は「配信中」のまま長さが入ることがあるので、終了時刻(`actualEndTime`)があるものは長さでは判定せず、ライブとして登録済みのものは `UULF` / `UUMF` に含まれると分かったときだけ動画にする。状態の追跡のため `live_status` は残し、API では動画として返す |
| ショート | `UUSH` に含まれるもの。プレイリストが使えないときは `/shorts/{id}` がリダイレクトされるかで判定 |
| 動画 | 上のどれにも当てはまらないもの |
| メンバー限定 | `UUMO` に含まれるもの(種別とは別に `members_only` を立てる) |

`UU` 以外のプレイリスト(`UUSH` / `UULF` / `UUMO` / `UUMF`)は YouTube の非公式な仕組みですが、広く使われています。

### クォータの目安(YouTube Data API)

上限は 1 日 10,000 ユニットです。Twitch の同期と、セトリの点検・曲の読み取りは、YouTube のクォータを使いません。

| 処理 | 1 日の目安 |
|---|---|
| 差分同期(5 分ごと、全チャンネル) | 1 回 1〜2 ユニット(`UUMO` の先頭と、予定・配信中があるときの `videos.list`)が 1 日 288 回で、1 チャンネルあたり約 300〜600 ユニット。これに、種別の一覧(`UUSH` / `UULF`)を確かめる回の 2 ユニットが、1 時間に 1 回(1 チャンネル 1 日 約 50 ユニット)と、新しい動画があったあとの 1 時間に加わる。RSS が取れなかった回は、代わりの問い合わせで 1 ユニット増える |
| 軽い確認(毎分) | 配信中のもの・開始が近い配信予定があるあいだだけ、1 回 1 ユニット。常に何かが配信中でも、1 日 最大 1,152 ユニット(288 回 × 4) |
| 合計の目安(6 チャンネル。偽の API で 1 日分を数えた値) | どのチャンネルにも先の日付の待機所がある静かな日で約 3,800、各チャンネルが配信 1 本・動画 1 本・ショート 1 本を出す日で約 4,800、常にどこかが配信中で RSS も 1 日取れない日で約 6,600(再生できるかの確認と再生リストの分は、上の数に含まない) |
| 再生できるかの確認 | 50 本で 1 ユニット。約 4,200 本なら約 84 ユニット |
| セトリの確認 | 1 回の確認で 1 ユニット(選んだコメントに返信があれば、もう 1 ユニット)。新しい歌枠 1 本につき 7 回確認するので、最大 14 ユニット。タイトルに「歌枠」が無い配信は 5 回なので最大 10 ユニット(多くは見つからずに 5 ユニット。1 日 1〜2 本ほどなので、1 日 10 ユニットほど) |
| 朝活のコメントの確認 | 1 回の確認で 1 ユニット(返信の取り足しが要れば、1 本あたり最大 3 ユニット増える。実際の朝活では要らなかった)。朝活 1 本につき 5 回確認するので 5 ユニット(1 日 1 本ほどなので、1 日 5 ユニットほど) |
| 再生リスト | 一覧の取り直しが 6 ユニット(1 チャンネル 1 ユニット)と、本数が変わった再生リストの読み直し(50 件で 1 ユニット) |
| プロフィール | 6 ユニット(1 チャンネル 1 ユニット) |

次のときだけ、一時的に増えます。

- **チャンネルを登録した直後**: 過去分の取り込みで、1 ページ(50 件)あたり 2 ユニット。
- **過去の歌枠のセトリを一通り確認するまで**: 1 回の実行で 10 本(1 本 1〜2 ユニット)ずつ進みます。約 1,000 本なら合計で約 1,000〜2,000 ユニット、半日ほどで終わります。
- **過去の朝活の配信のコメントを一通り確認するまで**: 1 回の実行で 5 本(1 本 1 ユニット)ずつ進みます。約 510 本なら合計で約 510 ユニット、9 時間ほどで終わります。
- **再生リストを最初に読むとき**: 6 チャンネル(再生リスト約 90 件)で約 150〜200 ユニット。

## 画面の実装メモ

### 時刻の表示

- 保存は UTC、表示はブラウザのタイムゾーン(日本なら JST)です。
- 月・週・リスト表示の時刻は **5 分単位で切り捨て** て表示します(例: 21:03 → 21:00)。配信は予定より数分遅れて始まることが多いためです。詳細ダイアログでは実際の時刻を表示します。

### 週・日表示(`TimeGridView`)

- ブロックの高さは、配信なら実際の長さ(予定は 1 時間、配信中は現在時刻まで)、動画は動画の長さです。短いものは読める最小の高さ(週 25 分 / 日 60 分ぶん)にそろえます。
- 時間が重なる予定は横に並べます。
- 予定は **配信を始めた日の列にだけ** 置きます。日付をまたぐ配信があれば、表示を 24 時以降(24:00, 25:00 … 最大 48:00)まで伸ばし、その時間帯は少し色を付けます。現在時刻の線は、前の日の列の 24 時以降にも引きます。
- 前の日に始まった配信は、次の日の列(日表示も)には出ません。
- 開いたときは、今日を含むなら現在時刻の少し前、それ以外は最初の予定の少し前までスクロールします。
- 週表示で日付の見出しを押すと、その日の日表示に切り替わります。

### 期間の移動とスワイプ

- 週・日表示も、その日を含む月グリッド(前後の週を含む)のデータで表示し、前後の月を先読みします。
- 表示中の月の予定は、画面を開いたままでも 1 分ごとに取り直し、タブに戻ったときにも取り直します(配信の開始・終了を反映するため)。
- スワイプは Motion のドラッグで実装しています。タッチ操作のときだけ反応し、縦スクロールはブラウザに任せます(`touch-action: pan-y`)。80px 以上動かすか素早く払うと移動し、スワイプのあとに指を離した位置の予定は開きません。

### 種別と Twitch の切り替え

- 切り替えの単位は「ライブ / 動画 / ショート / Twitch」の 4 つです(`src/shared/types.ts` の `EventFilter`)。Twitch のボタンは、Twitch にもチャンネルがあるものが登録されているときだけ出ます。
- Twitch の配信は、種別では「ライブ」です。そのため、ライブを非表示にすると Twitch も表示されません。このあいだ Twitch のボタンは押せず、ライブを戻すと、押す前の状態に戻ります。
- 件数は重ねて数えません。「ライブ」は YouTube のライブ、「Twitch」は Twitch の配信の数です。
- カレンダーでは読み込み済みの予定を画面側で絞り込み、検索ではサーバー側で絞り込みます(全件をたどれるようにするため)。
- チャンネルの表示・非表示も同じ場所で切り替えます。どちらの切り替えも URL には残りません。

### Twitch の配信とクリップ

- 配信中は Twitch のチャンネルのプレーヤー、終わったあとはアーカイブのプレーヤーを埋め込みます。Twitch の埋め込みは、埋め込む側のホスト名を `parent` で渡す必要があるので、表示しているページのホスト名を渡しています(`localhost` でも動きます)。
- 「この配信のクリップ」は、最初は 4 本だけ見せ、「すべてのクリップを見る」で残りを開きます。クリップを押すと、配信のプレーヤーの場所でそのクリップを再生し、「配信の表示に戻る」で元に戻ります。アーカイブが無い配信でも、クリップは再生できます。
- チャンネル情報の「クリップ」タブは、30 本ずつ読み込み、一覧の最後に近づくと続きを読み込みます。押したクリップは一覧の上で再生します。
- VS Code の内蔵ブラウザなど、動画の再生機能が限られたブラウザでは、Twitch のアーカイブを再生できません(エラー #4000)。確認は普段のブラウザで行ってください。

### 再生不可・限定公開の表示

- 再生できなくなったもの(`unavailableAt` があるもの)は、リストと検索では「再生不可」のバッジを付けてサムネイルとタイトルを薄くし、月・週・日表示では小さな印を付けてチップやブロックを薄くします。
- 詳細ダイアログでは、プレーヤーの代わりに「この動画は再生できません」と、確認した日付を表示します。セトリが残っていれば、そのまま見られます。
- 限定公開になったものには「限定公開」の印を付けます(再生はできます)。
- 絞り込みのボタンはありません。

### チャンネルの色で表すボタン

「楽曲リストを開く」ボタンは、チャンネルの色(`channels.color`)で表します。登録されている色は明るい色が多く、そのまま文字に使うと白い背景で読めないので、種別のボタンと同じく、薄い背景(12%)・半透明の枠線(45%)・濃い文字の組み合わせにしています(`src/client/index.css` の `.channel-tint`)。

- 文字とアイコンは、色相と鮮やかさを保ったまま、明るさだけをテーマに合わせます(`--tint-lightness`。ライトは 0.5、ダークは 0.82)。文字の基本色と混ぜる方法は、色相がずれる(黄色が赤茶に、緑が青緑に寄る)ので使っていません。
- この書き方(`oklch(from …)`)に対応していないブラウザでは、文字の基本色と半分ずつ混ぜた色になります。
- アイコンは、楽曲リストのサイトの favicon と同じ形を `ChannelDialog.tsx` に持っています。favicon は画像ファイルではなく HTML に直接書かれていて読み込めないためで、サイト側で変えたときは、こちらも差し替える必要があります。

### キーワード検索

- **全角・半角を区別しない仕組み**: SQLite には全角・半角をそろえる機能がないため、タイトルを NFKC で正規化して小文字にしたもの(例: `ＡＳＭＲ!` → `asmr!`、`ｼｬﾝﾌﾟｰ` → `シャンプー`)を `search_title` 列に保存しておきます。検索語も同じ規則でそろえてから、その列に含まれるかを `instr` で探します(`LIKE` は、D1 ではパターンが 50 バイトまでで、長い日本語の語を探せないため)。正規化の規則は `src/shared/search.ts` で、画面と Worker が共有しています。
- `search_title` が空の行(列を追加する前に登録したもの)は、元のタイトルを小文字にしたもので検索します。同期で順に埋まります。
- スペース(全角も可)で区切ると、すべての語を含むものに絞り込みます(5 語まで)。`%` や `_` は記号として扱います。入力が止まってから 0.3 秒後に検索します。
- **セトリの検索**: それぞれの語が、タイトルかセトリ(曲名・アーティスト)のどこかにあれば一致とします。「歌枠 曲名」のように、タイトルの語と曲名を混ぜて探せます。探すのは読み取った曲だけで、コメントの原文(挨拶や告知など)は対象にしません。セトリで当たった配信には、当たった曲を 3 曲まで表示します(残りは「ほか N 曲」)。
- セトリが見つかっていない歌枠、メンバー限定の歌枠、Twitch の配信は、セトリでは当たりません。セトリはファンの方が書いたものなので、同じ曲でも書き方(カタカナと英語、略称など)が違うと、書かれているとおりの語でしか当たりません。
- **全件のたどり方**: 一度に全件を描くと重くなるため、50 件ずつ取得し、リストの下に近づくと続きを読み込みます。ページの区切りは `event_at` と ID のカーソルです。最初のページで、切り替えの単位(ライブ・動画・ショート・Twitch)ごとの一致件数を数え、全件の件数を表示します。種別・Twitch・チャンネルの絞り込みはサーバー側で行います。
- 一致した語を強調表示します。600px 以上スクロールすると、右下に先頭へ戻るボタンが出ます。

### セットリストの表示

`src/shared/setlist.ts` の `parseSetlist` で、コメントの原文から曲だけを取り出します。書き手ごとに書き方が違うので、次のような形をまとめて扱います。

- 時刻: `0:06:19` / `00:09:46` / `03:14`。曲紹介・開始・終了の 3 つが並ぶ行は、曲の開始を使う
- 曲番号: `M01` / `🎶01.` / `01．` / `【01】` / なし(なければ 1 から振る)
- 曲名とアーティストの区切り: `／` / `/` / ` - `。コメントの中で一番多く使われているものを優先する(曲名に「/」を含む曲のため)
- 次の行に折り返した曲名・アーティストはつなげる。時刻だけの行の次の行に書かれた曲も読む
- 「3/30」「12／28」のように数字にはさまれた区切りは日付なので、曲名とアーティストの区切りにしない
- 曲以外の時刻(開始・OP・ED・告知・キリバンなど)と、補足(伴奏・作品名・発売日・リクエストした人・「少しアカペラ」などの演奏の補足・末尾の絵文字)は捨てる
- 「セトリ」の見出しがあり、その下(次の「タイムスタンプ」「雑談」などの見出しの手前まで)で 3 曲以上読めるときは、その部分だけを読む。セトリと目次(雑談も含む全体のタイムスタンプ)の両方に曲が書かれていても、セトリの方だけが出る
- 見出しが無く、同じ曲が 2 回書かれている場合や、日本語と英語で 2 回書かれている場合は、最初の 1 回だけにする(両方に番号が付いた歌い直しは残す)
- 「スタートライン!,アイカツスターズ / Start Line!, Aikatsu Stars!」のように、日本語と英語を「/」で分け、曲名とアーティストを「,」で区切ったセトリは、日本語の方を読む
- アーティストのあとに「,」で続く補足(「, ピアノ伴奏」「, New」)は外し、「鏡音リン, 鏡音レン」のような連名は残す
- 区切りが 1 つも無いときは、「セトリ」の見出しの下の行や「(歌)」の印の行を、曲名だけの曲として読む
- 番号が無い・重なったり戻ったりしているときは 1 から振り直す
- アーティストが書かれていないオリジナル曲は、`KNOWN_ARTISTS` の対応表で補う(例: Swing Days! → 碓氷ゆら。大文字・小文字は区別しない)

読み取りの結果が変わるように規則を直したときは、`SETLIST_PARSER_VERSION` を 1 つ増やしてください。検索用に保存してある曲が、同期のときに読み取り直されます(1 回の実行で 50 本ずつ。約 1,000 本で 2 時間ほど)。

曲が 1 曲も読み取れないとき(歌枠リレーの開会式など)は、セトリ欄を表示しません。セトリはファンの方が書いたものなので、一覧の下に書き手を表示しています。

### テーマ

ボタンで切り替えるまでは OS の設定(`prefers-color-scheme`)に合わせ、OS の設定が変わればそれに付いていきます。ボタンで選んだテーマは `<html data-theme>` と `localStorage`(キーは `prnb-stream-calendar-theme`。同じドメインのほかのサイトと重ならないように、サイトの名前を付けています)に保存します。`index.html` が読み込む `public/theme.js` で描画前に当てるので(CSP でインラインのスクリプトを禁止しているため、別のファイルにしています。CSP などの応答ヘッダーは `public/_headers`)、読み込み時に一瞬別の色になることはありません。色は `src/client/index.css` の CSS 変数で定義しています。

## セットアップ

### 1. YouTube Data API キー

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成
2. 「YouTube Data API v3」を有効化
3. 認証情報 → API キーを作成し、**API の制限** で YouTube Data API v3 のみに制限
   (サーバー側から呼ぶため、HTTP リファラー制限は設定しない)

### 1-2. Twitch のアプリ(Twitch の配信も表示する場合)

1. Twitch アカウントで 2 段階認証を有効にする
2. [Twitch Developer Console](https://dev.twitch.tv/console) →「アプリケーションを登録」。OAuth のリダイレクト URL は `http://localhost`、カテゴリーは任意、クライアントのタイプは「機密保持」
3. 作ったアプリの「管理」から、Client ID と Client Secret(「新しい秘密」で発行)を控える

### 2. ローカル開発

```bash
npm install
cp .dev.vars.example .dev.vars   # YOUTUBE_API_KEY と ADMIN_TOKEN(と TWITCH_CLIENT_ID / TWITCH_CLIENT_SECRET)を記入
npm run db:migrate:local
npm run dev                      # http://localhost:5173
```

初回データの取り込み(過去分が多い場合は数回実行):

```bash
curl -X POST -H "Authorization: Bearer <ADMIN_TOKEN>" http://localhost:5173/api/admin/sync
```

Cron の処理は `http://localhost:5173/cdn-cgi/handler/scheduled` を開くと手動で動かせます。

`.dev.vars` に入れていないものは、ローカルでは同期されません。`YOUTUBE_API_KEY` が無い(または無効な)ときは YouTube の同期が失敗し、Twitch だけが取り込まれます。`TWITCH_CLIENT_ID` / `TWITCH_CLIENT_SECRET` が無いときは、Twitch を同期しません。

### 3. Cloudflare へのデプロイ

```bash
npx wrangler login
npx wrangler d1 create prnb-youtube-calendar   # 出力された database_id を wrangler.jsonc に記入
npm run db:migrate:remote
npx wrangler secret put YOUTUBE_API_KEY
npx wrangler secret put ADMIN_TOKEN
npx wrangler secret put GITHUB_TOKEN      # セトリの点検の Issue 用(下記)
npx wrangler secret put TWITCH_CLIENT_ID      # Twitch の配信も表示する場合
npx wrangler secret put TWITCH_CLIENT_SECRET
npm run deploy
```

`GITHUB_TOKEN` は、GitHub の Settings → Developer settings → Personal access tokens → **Fine-grained tokens** で作ります。Repository access は このリポジトリだけ、Permissions は **Issues: Read and write** だけにします。トークンには有効期限があり、切れると Issue が作られなくなる(Workers のログに `setlist audit failed` が出る)ので、期限前に作り直して `secret put` し直してください。Issue を作るリポジトリは `wrangler.jsonc` の `vars.GITHUB_REPO` で指定します。

### 4. GitHub 連携(自動デプロイ)

1. このリポジトリを GitHub に push
2. Cloudflare ダッシュボード → Workers & Pages → `prnb-youtube-calendar` → Settings → Builds → **Connect** で GitHub リポジトリを接続
3. Build command: `npm run build` / Deploy command: `npx wrangler deploy`

以降は `main` への push で本番デプロイされます。`main` 以外のブランチの push ではプレビュー版がアップロードされ、本番には影響しません。

## 運用

### ブランチと本番反映の流れ

1. `develop` ブランチで開発して push する
2. スキーマを変更した場合は、**先に** 本番の D1 にマイグレーションを反映する(D1 のマイグレーションは自動では適用されません)

   ```bash
   npm run db:migrate:remote
   ```

3. `develop` を `main` に取り込んで push すると、本番にデプロイされる

マイグレーションは列の追加だけにしておくと、新しいコードのデプロイ前に反映しても、動いている本番に影響しません。データを書き換えるマイグレーション(`0017_recheck_split_setlists.sql` のように、新しいコードの動きを前提にしたもの)は、**新しいコードをデプロイしたあとに** 反映してください。

### 依存パッケージの固定(overrides)

`package.json` の `overrides` で、`undici` を `^7.30.1` に固定しています。開発用の `@cloudflare/vite-plugin` が使う `miniflare` が、脆弱性(GHSA-xjj6-f33q-929c など)のある `undici` 7.29.1 を固定で入れているためです。`undici` は開発サーバーだけで使われ、本番の Worker には入りません。`npm ls undici --all` で、`miniflare` が自分で 7.30.1 以上を要求するようになったと分かったら、この `overrides` を消してください。

### Cron(同期の間隔)を変えるとき

GitHub 連携の自動デプロイでは、コードは更新されても **Cron の設定は本番に反映されません**。`wrangler.jsonc` の `triggers.crons` を変えて `main` に取り込んだあと、プロジェクトのフォルダで次を実行してください。

```bash
npm run build                 # Cron の設定を含むデプロイ用の設定ファイルを作り直す
npx wrangler triggers deploy  # Cron の設定だけを本番に反映する
```

- 実行すると `schedule: * * * * *` のように、反映された設定が表示されます。ダッシュボードの Workers & Pages → `prnb-youtube-calendar` → Settings → Trigger events でも確認できます。
- 設定を変えてから実際の実行間隔が切り替わるまで、20 分ほどかかることがあります。切り替わるまでは前の間隔のまま実行されます(ダッシュボードの「Cron イベント」の `Cron` 列で、どちらの設定で実行されたかがわかります)。

### 同期の状態を確かめるとき

本番の D1 を直接見ると、同期が進んでいるかが分かります。日時は UTC です。

```bash
npx wrangler d1 execute prnb-youtube-calendar --remote \
  --command "SELECT label, synced_at, twitch_synced_at FROM channels ORDER BY sort_order"
```

`The given account is not valid or is not authorized to access this service [code: 7403]` というエラーが出ることがありますが、一時的なものなので、少し待ってやり直してください。

### チャンネルの追加

ID を 1 行追加するだけで、次の Cron から過去分の取り込みが始まります(タイトルとアイコンは自動取得)。

```bash
npx wrangler d1 execute prnb-youtube-calendar --remote \
  --command "INSERT INTO channels (id, color, sort_order) VALUES ('UCxxxxxxxxxxxxxxxxxxxxxx', '#f472b6', 1)"
```

2 チャンネル以上になると、画面にチャンネルフィルターと色分けが自動で表示されます。`sort_order` が画面での並び順です。 `color` には CSS の色をそのまま書けます。`var(--ink)` を指定すると、ライトテーマでは黒、ダークテーマでは白になります。`label` を入れると、チャンネルの表示・非表示を切り替えるボタンにチャンネル名の代わりに表示します(例: `公式`、`桃瀬にな`)。`songlist_talent` に楽曲リストのサイトの talent パラメータの値(例: `nina`)を入れると、チャンネルの詳細に「楽曲リストを開く」ボタンが出ます。

Twitch にもチャンネルがある場合は、`twitch_login` にログイン名(`twitch.tv/◯◯` の部分)を入れると、次の Cron から Twitch の配信も取り込みます。

```bash
npx wrangler d1 execute prnb-youtube-calendar --remote \
  --command "UPDATE channels SET twitch_login = 'xxxxxxxx' WHERE id = 'UCxxxxxxxxxxxxxxxxxxxxxx'"
```

チャンネルを増やすと、YouTube のクォータの消費が増えます(差分同期だけで、1 チャンネルあたり 1 日 約 350〜650 ユニット。「クォータの目安」を参照)。YouTube API の 1 日の上限(10,000 ユニット)に近づくので、増やす前に見積もってください(上限は Cloudflare のプランとは関係なく、Google Cloud でクォータの増枠を申請しないかぎり変わりません)。

## 既知の制限

- **メンバー限定から一般公開に変わった動画**: 「メン限」ラベルが付いたままになります。
- **予定日時を過ぎた配信予定**: 待機所が残っている限り、YouTube が「配信予定」として返すため、カレンダーにも予定として表示されます。
- **非公式のプレイリスト**: `UUSH` / `UULF` / `UUMO` / `UUMF` の仕様が変わると、ショート・プレミア公開・メンバー限定の判定に影響します。
- **Twitch の配信予定**: Twitch には待機所が無いため、配信予定は表示されません。配信が始まってから(5 分以内に)表示されます。
- **Twitch のアーカイブ**: 取り込めるのは、取り込みを始めた時点で Twitch に残っているものだけです。保存期間(7〜60 日)を過ぎると再生できなくなり、アーカイブを残さない配信は、配信中に取り込んだ記録だけが残ります(終了時刻は 5 分ほどずれることがあります)。
- **再生不可の表示**: YouTube の API では、削除と非公開を区別できません。気づくまでに最長で 1 日ほどかかり、表示する日付は「確認した日」で、実際に消された日ではありません。メンバー限定の動画が非公開・削除された場合も同じ扱いです。
- **Twitch のクリップ**: 削除されたクリップは、確認されるまで(最長 1 日ほど)一覧に残ります。アーカイブが無い配信のクリップは作成時刻で結び付けるため、配信が終わったあとに作られたものは配信に結び付かず、古いアーカイブから作られたクリップが、作った時刻に行われていた別の配信に結び付くことがあります。Twitch の API が返す全期間のクリップには上限があり(1,000 件ほど)、再生数の少ない古いクリップは取り込まれないことがあります。
- **YouTube と Twitch の同時配信**: 同じ配信が 2 件並んで表示されます。
- **検索の強調表示**: 半角カタカナの濁点(`ｶﾞ` など)を含む語は、検索では一致しても、強調表示されないことがあります。
